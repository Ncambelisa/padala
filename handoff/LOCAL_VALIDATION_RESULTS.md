## Browser validation performed

The production frontend was started locally with `npm run start -- -p 3400`. The FastAPI backend ran on loopback port 8000. Next's `/api/v1` rewrite successfully proxied to that backend. This is local-only validation, not a deployment.

The browser suite executed both desktop Chromium and mobile Chromium emulation. It covers:

- household registration, exact allocation totals, declaration submission, and OFW acceptance;
- visible wrong-password error handling;
- a separate sender and invited-member browser-context workflow: invitation acceptance and replay rejection, PHP 30,000 allocation plan, recipient acknowledgement, synthetic grocery receipt upload, notification, clarification request, member response, OFW acceptance, refresh persistence, and the persistent `Provider: not connected` label;
- 360px, 390px, 768px, and 1440px viewport checks for no horizontal scroll, plus keyboard open/escape-close behavior for the New Padala dialog.

The viewport matrix is intentionally skipped in the `mobile-chromium` Playwright project because it creates its own contexts at every required width. The two-account end-to-end flow runs in both desktop and mobile projects.

## Production-hardening update — 2026-11-03

**Scope:** Code-level production safeguards only. All validation remained local,
used a temporary database, fictional users, and a synthetic receipt. No customer
data, PostgreSQL/Redis/ClamAV/SMTP/Azure provider, payment provider, public host,
or external deployment was used.

### Changes validated

- Explicit `PADALA_ENV=production` now fails closed unless HTTPS cookie/origin/
  host controls, PostgreSQL via psycopg, TLS Redis rate limiting, private malware
  scanning, SMTP STARTTLS, and a separate outbox worker are configured.
- The backend accepts an internal proxy origin only when the direct caller is from
  an explicitly configured `TRUSTED_PROXY_NETWORKS` CIDR. This supports the Next
  proxy without allowing arbitrary forwarded-origin or forwarded-IP input.
- Receipt uploads run a ClamAV-compatible `INSTREAM` scan before bytes are stored;
  a required unavailable scanner returns an error instead of storing the file.
- API responses include request correlation IDs and extra browser isolation
  headers; API OpenAPI/docs endpoints are disabled in production mode.
- The web application applies a fresh nonce-based CSP in production, with no
  production `unsafe-eval`; it dynamically renders the page so framework scripts
  receive the nonce.
- A GitHub Actions CI workflow now runs backend tests plus frontend typecheck,
  production build, and high-severity npm audit.

### Xendit subscription implementation update — 2026-11-04

**Scope:** Selected Xendit as the only subscription provider in code. Added a
disabled-by-default hosted checkout flow for Padala Basic (PHP 99/month; up to
four active household members) and Padala Family (PHP 149/month; up to eight),
a server-side provider adapter, one-month first-enrollment trial, signed webhook
lifecycle, one subscription per household, cancellation request, public terms
shell, and optional paid-access gate. No Xendit account, payment credential,
live callback, charge, customer, refund, invoice, provider fee, or public
deployment was used.

**Security and product behavior:** The frontend never receives a Xendit secret
or collects payment details. It redirects only to a validated Xendit hosted
checkout URL. The API accepts the public callback only with the configured
`x-callback-token`, verifies amount/currency/reference/session or plan IDs,
retains a SHA-256 callback digest instead of raw payloads, and treats duplicate
delivery as idempotent. Browser return pages cannot activate access. A signed
plan-activation callback starts the first household trial; at trial end, a
signed successful recurring-cycle callback is required to retain access. A
cancellation keeps current access during the `cancellation_pending` state and
removes it only after the signed plan-inactivation callback.
